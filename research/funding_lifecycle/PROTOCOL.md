# Phase 4C: synthetic Funding lifecycle

This additive package is an in-memory mathematical fixture component. It has no
network client, market-data loader, snapshot adapter, production command or link
to the historical Stage-0B runner. It neither reads nor changes that runner's
private accounting. The frozen specification and official research configuration
remain authoritative. This protocol does not amend either authority.

## Input and ownership

Construct a `FundingLifecycle(FixtureCalendar, Scenario)` and submit immutable
`Boundary` objects to `advance`. All owners must explicitly carry
`SYNTHETIC_FIXTURE_ONLY`, a `fixture:` identity, one existing C01–C12 candidate
identity and a separate partition identity. Existing `Period.annual(2023/2024)`
authorization is reused. There is no historical-evidence input mode. Strings,
paths, client objects and alternate calendar types are rejected before I/O.

The calendar is an explicit, ordered, unique tuple of expected synthetic
settlements, including every settlement relevant to that fixture's modeled
timeline. `complete=True` is an assertion about this constructed fixture only.
Skipped expected timestamps, duplicates, unknown coverage, unregistered
settlements and out-of-partition inputs fail closed. It is impossible to certify
an actual historical calendar through this API. A fixture with an empty expected
schedule asserts no settlements for that synthetic experiment only.

Quantity is a positive integer number of frozen 0.001-BTC steps. Decimal inputs
must be finite `Decimal` objects; binary floats and implicit numeric conversions
are rejected. IDs are unique within one path and reset in a newly constructed
independent partition. Invalid owners, directions, fills, quantities, repeated
settlements and inconsistent attribution fail with deterministic errors. Each
boundary is transactional: validation and updates occur on a trial copy, and a
failed boundary leaves the original state unchanged.

## Arithmetic and accounting

Long Funding is `-q * mark * rate`; Short Funding is `+q * mark * rate`. A positive
rate means Long pays and Short receives. Negative rates reverse those signs.
Explicit zero is valid; missing or malformed rate is never substituted with zero.

Decimal coefficient/exponent arithmetic computes exact finite products and sums
without reliance on the process Decimal precision. There is no cash rounding,
quantization or tolerance policy. Decimal values serialize as exact strings;
display formatting never feeds accounting. A Fraction-based expectation and
literal independently calculated results test the arithmetic.

An Entry records original steps, direction, fill identity and timestamps. Each
Exit reduces remaining steps once. Quantity conservation and unique per-entry
Funding records are checked after every successful boundary. Global records
retain scenario, settlement and proxy provenance; entry records retain their
own events and exact cumulative Funding. Completed and censored positions are
separate collections. Unallocated structural exemptions never attach to a later
entry.

`Entry.cash_after` and `Exit.cash_after` are explicit, synthetic pre-Funding
execution snapshots, not calculated execution proceeds. Cash changes only on
those execution inputs. Settled-flat balance changes only at complete execution
closure. UTC day-start uses the last settled-flat snapshot, and the frozen daily
stop comparison is reproduced using only those snapshots. Funding never enters
cash, sizing balance, day-start, daily-stop or entry eligibility. Margin is not
simulated; its shared marker stays `PRE_FUNDING_MODEL_NOT_EXECUTED` for all
scenarios. Existing Stage-0B margin tests remain separate regression evidence.

## Boundary phases

The relevant sequence is PRIOR_BAR, PARTITION_END if applicable, UTC_DAY_RESET /
initial flat partition state, FUNDING, SIGNAL_CLOSE, OPEN and INTRABAR.

PRIOR_BAR fills have `time_ms=t` and `bar_open_ms=t-15m`. They are economically
before Funding(t), including previous-bar exits displayed at bar-end t. At UTC
midnight they belong to the previous day, before the new day's reset. Sparse
synthetic timelines advance intervening day snapshots before their prior-bar
fills; no intervening price path is invented.

At annual end only PRIOR_BAR executes. Residual exposure is censored with its
existing Funding, and excluded Funding/entry/OPEN payloads are not processed.
A new annual instance starts Flat with no pending order, attribution or carried
IDs, and fresh synthetic 10,000-USDT shared snapshots.

SIGNAL_CLOSE accepts a predeclared fixture entry only when the original shared
path is eligible and Flat. Its signal-close timestamp equals the next bar's
OPEN timestamp t, representing the close of the previous execution bar; no
signal is generated by this component. The entry fills at OPEN after Funding.
An explicit immediate OPEN exit of that new entry is retained. Same-bar
INTRABAR exits are represented at the next boundary as PRIOR_BAR with
`INTRABAR_TIME_UNKNOWN`, without inventing an intrabar fill timestamp or deriving
ordering from candle extremes. No broker emulator is implemented.

## Six scenarios and tie handling

The three Mark fields are previous completed one-minute Close, Low and High.
Each combines with the two registered old-OPEN-exit precedence models:

- `FUNDING_BEFORE_OLD_OPEN_EXIT`: use old remaining exposure after PRIOR_BAR.
- `OLD_OPEN_EXIT_BEFORE_FUNDING`: use old remaining exposure after those same
  predeclared OPEN exits, solely for Funding exposure determination.

The alternate model validates old OPEN exits on a shadow state. It does not
advance real shared execution state or free occupancy at SIGNAL_CLOSE. Actual
execution events retain their frozen phase order and inputs in both scenarios.
Partial/full old OPEN exits register `FUNDING_TIE`. New same-OPEN entries remain
exempt. An alternate full old OPEN exit yields structural zero exposure even
if rate/Mark evidence is absent; no synthetic rate or price is invented.

With positive exposure, settlements off the 15-minute execution boundaries
raise `FUNDING_ALIGNMENT_UNRESOLVED`. Zero old exposure may be explicitly
classified without multiplication. Supplied evidence is still validated; the
exemption never authorizes arbitrary malformed or out-of-period evidence.

All Mark variants require the exact completed minute `[t-60000ms, t)` with finite,
positive OHLC and valid geometry. Canonical provenance remains
`APPROXIMATE_MARK_PREVIOUS_1M_CLOSE`, with the actual selected field explicitly
recorded. `exact_tick=false` and `guaranteed_settlement_bounds=false` are required.
Low/High are sensitivity proxies, not exact settlement ticks or guaranteed
bounds. Duplicate, conflicting, incomplete, unlinked or substitute evidence fails.

The initial 2023 missing prior minute is exempt only because initial old
exposure is provably zero. No pre-2023 candle or invented zero rate is inserted.
This does not repair raw-snapshot missingness or establish calendar completeness.

## Verification and limitations

`tests/test_funding_lifecycle.py` exercises the requested A–AD cases, independent
arithmetic expectations, transactional failures, T16, censoring and exact replay.
`tests/run_phase4c_regression.py` is a test-only guarded discovery harness. It
denies repository data access and network traffic before access, denies
repository writes, and allowlists read-only Git checks plus the frozen
environment's `uname -p` / `file -b <Python executable>` probes. Temporary
synthetic files used by unmodified historical tests are allowed outside the
repository. An unexpected prohibited access aborts, rather than adding a skip.

Only the two specifically user-approved real-cache tests are skipped in guarded
regression. Every new fixture test executes. Full historical regression is
**NOT FULLY RE-EXECUTED**; previous pass evidence is preserved by Git and hashes.
The report gives exact IDs, reasons and separate counts. `--focused` runs the
entire new module under the same guards; `--replay-hashes` exports only hashes of
paired in-memory synthetic replays, never an accounting ledger.

Serialized fixture output always retains historical Funding `PARTIAL_DATA`,
calendar `UNVERIFIED`, and official research `NOT_EVALUABLE` status. This phase
does not integrate Funding with real positions, repair calendars, evaluate net
historical results, run Holdout sensitivity tests or verify TradingView execution.
Those gates require separately authorized work and remain open.
